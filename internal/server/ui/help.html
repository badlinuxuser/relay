Quick start

  1. Start Relay. Run relay in the folder you want to work in. The background service starts by itself.
  2. Add keys for the cloud providers you use: type /keys. A page opens in your browser where you paste a key for each provider. Keys are saved on your computer and work immediately. Local models (Ollama, llama.cpp) need no key.
  3. Pick a model: type /models, move with ↑ ↓ and press enter. Or leave it on auto and let the current mode choose.
  4. Chat. Type a message and press enter. Press ctrl+a to let the model work with the files in your folder (agent mode).
Tip. In Relay, /help opens this page again and /keys opens the keys page.

The screen

  • Header: current mode and whether agent mode is on.
  • Feed (left): your messages, the answers (with the model that wrote them under each answer), tool calls of the agent, and notices. Scroll with pgup / pgdn or the mouse wheel.
  • Input (bottom): a message, or a command that starts with /.
  • Side panel (right, wide terminals only): the mascot and its mood, and the current mode, model, agent state, working folder, tokens (in / out) and cost of this session.

The mascot reacts to what happens: it is happy when an answer arrives, notices tool calls and key switches, is surprised by errors and approval requests, and gets tired when a key hits its rate limit or when nothing happens for a while. The colour of the whole interface follows the mode.

The model row shows the model you chose, or, on auto, the first model of the current mode that can actually be used right now.

Choosing a model

Type /models. A list opens above the input line. Text after the command filters it: /models gemini, /models cloud, /models qwen coder (all words must match).

Where the list comes from

Relay asks every provider which models it really has, so you do not have to write model names into a config file:

  • Ollama (on this computer): everything you have installed (ollama list). Shown as ollama/<name>. Cloud models that your local Ollama forwards (names ending in -cloud) appear here too.
  • Ollama cloud: add an Ollama key on the keys page and the models of your ollama.com account appear as ollama-cloud/<name>.
  • Gemini, Anthropic, OpenAI, Grok, DeepSeek, OpenRouter: add the key and the provider's own model list appears (gemini/<name>, anthropic/<name>, …). Models that are not for chat (embeddings, speech, images) are left out.

What you see

  • Order. The model makers' own APIs come first (Anthropic, OpenAI, Gemini, Grok, DeepSeek), then everything else: Ollama, Ollama cloud, llama.cpp, OpenRouter, and so on.
  • Only what you can use. A provider without a key, with a key it refuses, or a local server that is not running adds nothing to the list. Errors are not shown in the terminal: open /keys to see them next to the provider.
  • Fresh. The list is cached for a minute. Adding or deleting a key refreshes it at once, so after /keys just type /models again.
  • auto (the first line) means "no fixed model": the current mode picks from its chain.

Good to know

  • The model stays selected for the current session until you choose another one or auto. A new session starts on auto.
  • If the chosen model fails because of a rate limit or a server error before it has written anything, Relay tries the next model of the mode.
  • Prices are not known for models that were found automatically, so their cost shows as $0.00; tokens are still counted. To track cost, add the model to config.toml with price_in / price_out (see Configuration).
  • Not every model can use tools. If agent mode answers with an error such as "does not support tools", pick another model.

Modes

A mode is a colour theme plus a chain of models: Relay tries the first model; if it is out of quota, has no key or fails, it moves to the next one.

ModeColourMeant for
smallgreenQuick questions, local and cheap models. Starts with your local Ollama models.
mediumpurpleEveryday coding and writing with a stronger cloud model.
hardredDifficult tasks; the strongest models first, longer agent runs.
maximumrainbowSame models as hard, the longest agent runs.

Switch with ctrl+t or /mode. The chains and the agent step limit of each mode are in config.toml ([modes.small] and so on).

Models of the chain that have no key, or that a local server does not have installed, are skipped quietly. If a local model from the chain is not installed, the models you do have installed take its place.

API keys

/keys (or relay keys in a terminal) opens the keys page on your own computer. For each provider you can add one or several keys, give them labels, and delete them. After a key is saved the page asks the provider which models the key opens and shows the number, or the provider's error if the key is wrong.

ProviderGet a keyNotes
anthropicconsole.anthropic.comClaude models.
openaiplatform.openai.comGPT models.
geminiaistudio.google.comGoogle Gemini API. Only models that can generate text are listed.
grokconsole.x.aixAI Grok models.
deepseekplatform.deepseek.comDeepSeek models.
ollamaollama.com/settings/keysLocal models need no key. A key unlocks Ollama cloud models (ollama-cloud/…). The same key is used for both.
openrouteropenrouter.ai/keysMany models from many makers through one key.
llamacppnoneLocal server (llama-server), no key needed.

Several keys for one provider

Add as many as you like. While one works, Relay keeps using it. When a key hits its rate limit or runs out of credit, Relay switches to the next key (you see a notice), and the tired key rests for two minutes. When all keys are used up, it moves on to the next model of the mode.

Where keys are stored

In keys.json in the Relay folder, readable only by you. They never leave your computer except in requests to the provider they belong to. The page shows only the last four characters. Environment variables also work if you list them in the config (api_key_env = ["MY_VAR"]), but you do not need them.

Local models

Ollama

  1. Install Ollama from ollama.com/download.
  2. Download a model: ollama pull granite4.1:3b (any model from the Ollama library).
  3. If Ollama is not already running, type /start ollama. If it is (for example as a system service), Relay simply uses it and never stops it.
  4. Type /models: your models are listed as ollama/….

llama.cpp, LM Studio, vLLM and others

Any server with an OpenAI-compatible /v1 API works. llama.cpp is preconfigured on port 8080. For others add a provider to config.toml (see Configuration). To let Relay start the server for you, add a [[processes]] entry and use /start <name> and /stop <name>.

A local server that is not running is not an error: its card on the keys page says "not running" and it adds nothing to the model list.

Agent mode

Turn it on with ctrl+a (the header shows agent on). The model can then work with the folder where you started Relay, in steps: it looks at files, changes them, runs commands, and reads the result before the next step.

ToolWhat it doesAsks you first?
read_fileRead a file in the folder.no
list_dirList a directory.no
grepSearch text in files.no
web_fetchDownload a web page and read it.no
write_fileCreate or overwrite a file.yes
edit_fileReplace part of a file.yes
run_shellRun a shell command.yes
MCP toolsTools of MCP servers from the config.yes

When approval is needed, the input box turns into a question showing what is about to happen. Answer y (once), a (always for this tool in this session) or n.

The number of steps for one request is limited by the mode (10 in small, up to 40 in maximum). When the limit is reached, send another message to continue.

Agent mode needs a model that supports tool calls. In automatic mode Relay skips models marked without tools; if you pick a model yourself and it cannot use tools, the provider will say so.

MCP servers

Add a [[mcp]] entry to config.toml and its tools become available to the agent:

[[mcp]]
name = "fs"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/dir"]

Compare models

Send one prompt to several models at the same time and read the answers one under another:

/compare ollama/granite4.1:3b gemini/gemini-2.5-flash Explain what a mutex is in two sentences.

List up to four model ids first (ids from /models, or short names from the config), then the prompt. The active system preset is used; agent tools are not.

Sessions & presets

Every conversation is a session saved on disk. /new (ctrl+n) starts a fresh one in the same folder and mode. /sessions lists the latest ones, /load <id> brings one back with its full history. You can change the mode, model and preset in the middle of a conversation; the next message uses the new settings.

A preset is a system prompt. /preset coder makes the model a careful software engineer, /preset concise asks for short answers, /preset none removes it. Add your own with [[presets]] in the config.

Configuration

Relay works without any configuration. To change anything, edit config.toml. Print its location with relay config; print the full commented example with relay config --example.

Restart needed. The config is read when the background service starts. After editing it run relay stop, then relay again. The file is created once and never overwritten, so new Relay versions do not change your edits.

Add a provider

Any OpenAI-compatible server:

[[providers]]
name = "lmstudio"
kind = "openai"
base_url = "http://127.0.0.1:1234/v1"

Its card appears on the keys page and its models in /models. Optional fields: api_key_env (read keys from environment variables), headers (extra HTTP headers), discover ("none" turns the model search off for the provider; other values force a search style: ollama, gemini, anthropic, openai), key_from (use the keys of another provider, as ollama-cloud does).

Give a model a short name, a price, and a place in a mode

[[models]]
id = "flash"                 # short name you can type: /models flash
provider = "gemini"
model = "gemini-2.5-flash"   # the provider's own name
tier = "small"
tools = true                 # the model can call tools (needed for agent mode)
price_in = 0.30              # USD per 1M input tokens, for the cost counter
price_out = 2.50

[modes.small]
models = ["local-small", "flash"]   # the chain: tried in this order
max_steps = 10

Other sections

  • listen: address of the background service (default 127.0.0.1:8787).
  • workspace: fixed folder for the agent (default: the folder where Relay was started).
  • default_mode: mode of a new session.
  • [[processes]]: local servers that /start and /stop manage, with command, args, ready_url and autostart.
  • [[presets]]: your own system prompts.

OpenAI-compatible API

While Relay is running, other programs can use it as an OpenAI endpoint. They get Relay's routing, key rotation and cost tracking, and you keep all your keys in one place.

# the access token is in the "token" file in the Relay folder
TOKEN=$(cat ~/.config/relay/token)

curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"model":"relay-medium","messages":[{"role":"user","content":"Hello"}]}'

Settings for other tools: base URL http://127.0.0.1:8787/v1, API key = the token.

model can be relay-small / relay-medium / relay-hard / relay-maximum (use that mode's chain), auto (Relay chooses a mode by the size and kind of the request), or any model id from /models such as ollama/granite4.1:3b. GET /v1/models lists them all. Streaming works; tool calls are not supported through this endpoint.

The full description of the backend API is in docs/PROTOCOL.md in the Relay repository.

Where Relay keeps its files

Linux: ~/.config/relay/ · Windows: %AppData%\relay\ · macOS: ~/Library/Application Support/relay/. Set RELAY_HOME to use another folder.

  • config.toml: settings
  • keys.json: your API keys
  • sessions/: saved conversations
  • usage.json: token and cost totals per model
  • token, daemon.json: access token and address of the running service
  • relayd.out: output of the background service (look here if it does not start)

Troubleshooting

The model list is empty or a provider is missing

  • No key? Add it with /keys. Providers without a key are skipped.
  • Open /keys and look at the badge next to the provider: it shows how many models were found, or what the provider answered (for example "API key not valid").
  • Ollama: make sure it is running (/start ollama) and that you have pulled a model (ollama list).
  • Just added a key? Type /models again; the list refreshes by itself.

"model not found" from a provider

A model name from config.toml may be outdated. Pick a model from /models instead; those names come straight from the provider.

"no API key for …"

The model you chose belongs to a provider without a key. Add one with /keys, or pick another model.

"rate limit" or the mascot looks tired

The key's quota is used up. Relay switches to another key or model automatically. Add more keys, or wait a couple of minutes.

The interface does not start or says the service did not start

Read relayd.out in the Relay folder, or run relay daemon in a terminal to see the error. A broken config.toml is the usual reason; the message names the line.

The old settings are still used after I edited the config

Run relay stop and start relay again.

The side panel or the mascot is not shown

The side panel needs a terminal at least 104 columns wide. The mascot also needs enough height.

Odd characters like [<64;101;29M in the input

That is a mouse wheel report that a busy terminal split in two. Relay removes it automatically. If your terminal keeps doing this, scroll with pgup / pgdn instead.

Privacy & safety

  • The Relay service listens only on 127.0.0.1, requires the access token and checks the Host header, so other computers and web pages cannot talk to it.
  • Your keys are stored in a plain text file readable only by you. The terminal and the pages never show more than the last four characters.
  • Your messages go only to the provider of the model you use. Relay has no servers of its own and sends no telemetry.
  • The agent can read and write files only inside its working folder (symbolic links are not checked). Writing, editing, shell commands and MCP tools always ask first.
  • The shell is not sandboxed: run_shell can do anything you can do. Read each command before you press y, and be careful with a.
